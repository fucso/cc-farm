# graze

- GitHub Issue を1件読み、実装して、プルリクエストを作成するスキル。
- 実装の進め方そのものは pstack に委譲し、このスキルは入口・出口・ガードレールだけを持つ。

## 引数

- issue（必須）: 現在のリポジトリの Issue 番号または URL。$ARGUMENTS で受け取る。
- issue が無い場合は、他のことをする前にまず聞く。

## 前提

- commons プラグインがインストールされていて、/commons:common-sense の規約（状態モデル、コメント規約、PR 規約）を参照できること。
- pstack プラグイン（michael-denyer/pstack-claude）がインストールされていて、/pstack:poteto-mode と /pstack:interrogate が使えること。
- gh が利用可能で、認証済みであること。

## 手順

1. Issue の確認
   - 次のコマンドで Issue を取得し、タイトルと本文をタスクとして扱う。

     ```
     gh issue view <issue>
     ```

   - その Issue を参照する open なプルリクエストが既にないか確認する。
   - 既にある場合は、重複して着手せず、その旨を報告して止まる。
2. ブランチ作成と着手
   - 次のコマンドで、その Issue 用のブランチを作って Issue と紐付ける。

     ```
     gh issue develop <issue> --checkout
     ```

   - 紐付けと同時に、Issue のステータスラベルを farm:in-progress に付け替える。
3. 実装
   - Issue のタイトルと本文をタスクとして /pstack:poteto-mode を起動する。
   - 完了条件として「実装と検証までで終わること」を付け加える。プルリクエストの作成と CI 対応は後続の手順で行うため、poteto-mode 側では行わない。
   - playbook は指定しない。poteto-mode のルーターに選ばせる。
   - 検証は poteto-mode の仕事であり、リポジトリに project の verify スキルがあればそれを使うのも poteto-mode 側の判断に含まれる。
   - この環境で実検証が不可能な場合は、証跡を偽らず、その旨をプルリクエスト本文に明記する。
   - 作業中に Issue の範囲を超える問題が見つかった場合は、「終了手順」に従って止まる。
4. 自己レビュー
   - 差分に対して /pstack:interrogate を実行する。
   - "act on" に分類された指摘は直す。
   - それ以外で重要なものは、プルリクエスト本文に残して見えるようにする。
5. プルリクエスト作成
   - コミットは小さく、レビューしやすい単位に分ける。
   - プルリクエストはドラフトで作成する。
   - 本文には Closes #<issue> で Issue をリンクし、変更の概要と検証の証跡（実行したことと観測した結果）を書く。
   - マージはしない。
6. CI 監視
   - プルリクエストのチェックを監視し、自分の変更が原因の失敗は直す。
   - 無関係な失敗や環境起因の失敗は、追いかけずに報告する。
   - CI がグリーンになったら監視を終える。その後に届いたコメントには反応しない（それは mend の仕事）。
7. プルリクエスト情報のレビュー
   - プルリクエストのタイトルと本文だけを確認する。コードは見ない（コードのレビューは interrogate の担当）。
   - 次の2点を満たしているか確認し、満たしていなければ直す。
     - poteto-mode 側の規約に沿っている。
     - farm の必須要件（Closes での Issue 紐付け、検証の証跡）が入っている。
8. レビュー待ちへの移行
   - プルリクエストを ready for review にする。
   - Issue のステータスラベルを farm:in-review に付け替える。
   - 正常終了時の結果コメントは書かない。

## 終了手順

- 作業を続けられない場合の止まり方。
- 理由ごとに、Issue のステータスラベルを付け替えてから終了する。
  - 隠れた依存が見つかった: farm:blocked に付け替える。
  - 人間の判断が要る、内容が曖昧、既に完了している、自分では解消できない理由でブロックされている: farm:needs-human に付け替える。
- 付け替えたら、理由を Issue にコメントする。
- コメントの先頭には、common-sense が定める farm マーカーを入れる。
- 明確な停止も正常な結果である。

## ガードレール

- 対象の Issue の範囲だけで作業する。他の作業のアイデアは差分に入れず、コメントを書く事態のときにだけ書く。
- マージはしない。Issue を手で閉じない（プルリクエストの Closes が閉じる）。
- ステータスラベルは常に1つまでにする。
- コメントは、ラベルで表現できない事態のときだけ書く。
